# 产出物三 · 可调试的 Harness

**状态：未开始**

## 目标

前两个产出物是「能跑」。这一个的目标是「**跑得稳、跑得便宜、出问题查得到**」。

这一步是整个学习路径里最值钱的部分——招聘 JD 里反复出现的 Harness Engineering，说的就是这个。也是纯后端能力最能直接迁移的地方。

前置：产出物一、二都已经跑通。

## 题目

给前面做好的程序加一层「外壳」，让它具备生产环境的基本素质。不改业务逻辑，只加保障。

## 硬性要求

| 加什么 | 具体要求 | 想清楚 |
|---|---|---|
| 超时 | 单次模型调用、单次工具调用都要有超时 | 超时后是重试还是直接失败？ |
| 重试 | 工具失败要能重试，不能整个任务崩 | 什么样的错误该重试、什么不该？（是不是幂等问题？） |
| 限流 / 配额 | 单次任务最多调用多少次模型、多少次工具 | 超了怎么优雅退出 |
| 成本统计 | 记录每次任务的 Token 消耗和调用次数 | 成本失控通常是哪种情况引起的？ |
| 链路追踪 | 一次任务的所有步骤能串起来查（给每次任务一个 ID） | 这和你的日志/链路追踪经验是一回事吗？ |
| 敏感操作确认 | 危险工具（比如写文件、删数据）执行前要人工确认 | 这就是 HITL，和你熟悉的审批流有什么异同 |

## 要搞明白的问题

- 上面这六件事，**哪几件你在后端项目里已经做过了**？换个场景为什么还要重做一遍？
- Agent 的「失败」和后端接口的「失败」有什么不同？（提示：Agent 可能失败得**不报错**——答案看起来对，其实是错的）
- 如果只能保留一项，你保哪个？为什么？

## 验收标准

- [ ] 把模型 API 地址故意改错，程序能重试并给出可读的失败原因，而不是抛一堆堆栈
- [ ] 一次任务能查到完整的过程记录（任务 ID → 每一步 → 耗时 → 消耗）
- [ ] 危险工具确实拦得住，需要确认才执行
- [ ] 能拿这套东西去讲清楚：**「让 Agent 能跑」和「让 Agent 在生产跑」差在哪**

## 提示（卡住了再看）

<details>
<summary>关于「失败得不报错」</summary>

接口挂了会抛异常，你一定知道。但 Agent 可能给你一个格式完美、语气笃定、内容全错的答案，程序层面一切正常。这是它和传统后端最本质的差别——所以「评测」才成为 Agent 工程里独立且重要的一环。

</details>
