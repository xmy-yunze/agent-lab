# 产出物二 · 资料研究助手

**状态：未开始**

## 目标

把「工具调用 + 检索 + 记忆」三件事装到一起，做出一个能自己翻资料回答问题的东西。

前置：产出物一已经跑通。

## 题目

改造产出物一的程序，让它能回答关于**一个本地文件夹**的问题。

> 场景示例：把几份项目文档丢进一个目录，然后问「这个项目的登录接口有几个校验点？」
>
> 程序需要自己决定：先看看目录里有什么 → 挑相关的文件读 → 提取内容 → 组织答案。

## 硬性要求

1. **工具升级**：至少要有「列出目录」「读文件」「检索关键词」三个工具，由模型自己选。
2. **检索先用最笨的办法**——关键词匹配或简单打分就行，**不要上向量库**。这一步的目的是先看清「检索结果是怎么被塞进上下文」的。
3. **多轮记忆**：同一个会话里连续追问，它要记得之前聊过什么。
4. **必须给上下文设上限**。超过上限时要处理——想清楚是丢掉最早的、还是压缩成摘要。
5. **能在回答里指出**结论来自哪个文件的哪一段。

## 要搞明白的问题

- **「记忆」和「上下文」是两个东西吗？** 分别存在哪、活多久？
- 上下文撑爆了怎么办？丢弃和压缩各有什么代价？
- 检索出来的内容怎么塞进提示里？塞多了会怎样、塞少了会怎样？
- 为什么要求「指出结论来自哪个文件」？这和**幻觉**是什么关系？
- 你熟悉的**后端缓存分层**（本地缓存 → Redis → DB），和这里的「上下文 → 记忆 → 检索」是不是同一个结构？

## 验收标准

- [ ] 能回答一个需要**读两个以上文件**才能回答的问题
- [ ] 答案里带文件出处
- [ ] 连续追问三轮，它还知道你前面问了什么
- [ ] 故意把超大文件丢进去，程序不会崩

## 提示（卡住了再看）

<details>
<summary>关于记忆和上下文的区别</summary>

上下文是这一轮对话发给模型的全部内容，有硬上限。记忆是持久化下来的东西，存在磁盘或数据库里，可以无限长。每一轮从记忆里「捞」一部分出来放进上下文——注意这跟你做分页查询、查缓存时的取舍是不是同一个问题。

</details>

<details>
<summary>关于出处和幻觉</summary>

要求模型说清「哪句话来自哪个文件」是压制幻觉最有效的土办法：它没有出处可引时，就不敢编。这也是 RAG 系统里「引用溯源」的雏形。

</details>
